> [!abstract] Accounting and Session Management
> **Accounting** is the third and final pillar of the **AAA Framework** (Authentication, Authorization, and Accounting). It involves tracking and monitoring **access logs** to maintain visibility over user actions. Managing online interactions relies on **sessions**, **session IDs**, and **cookies**—mechanisms that improve efficiency but must be defended against threats like **session hijacking**.

---

# Accounting: The Third Pillar of AAA

> [!info] Definition
> **Accounting** is the practice of collecting, monitoring, and analyzing system access logs to track user activities, resource consumption, and administrative events.

Accounting answers three essential questions:
1. **Who** accessed the system?
2. **When** did they access it (timestamp & duration)?
3. **What** specific resources, files, or services did they interact with?

### The Security Analyst's Role in Log Analysis
Access logs are the backbone of security operations and are typically the **first artifact** examined during an incident investigation:
- **Trend Identification:** Spotting anomalies like repeated failed login attempts (indicating brute force or credential stuffing).
- **Intrusion Detection:** Uncovering unauthorized access, lateral movement, or policy violations.
- **Incident Response & Forensics:** Reconstructing an attacker's timeline and scope during a data breach.

# Sessions and State Management

Because HTTP is a stateless protocol, systems initiate a **session** to maintain continuity across user requests.

> [!info] Session Definition
> A **session** is a continuous sequence of network requests and responses associated with a single authenticated user, spanning from the moment they log in until they log out or the connection times out.

```
                      ┌────────────────────────────┐
                      │   USER LOGS IN / ENTERS    │
                      └─────────────┬──────────────┘
                                    │ Triggers
            ┌───────────────────────┴───────────────────────┐
            ▼                                               ▼
   ┌─────────────────┐                             ┌─────────────────┐
   │   SESSION ID    │                             │ SESSION COOKIE  │
   │  Unique device  │                             │ Temporary token │
   │ & user token    │                             │ stored on client│
   └────────┬────────┘                             └────────┬────────┘
            └───────────────────────┬───────────────────────┘
                                    ▼
                      ┌────────────────────────────┐
                      │    STATEFUL INTERACTION    │
                      │ (No passwords re-sent)     │
                      └────────────────────────────┘
```

When a session begins, two synchronized actions take place:

| Component | What It Is | Function & Lifecycle |
| :--- | :--- | :--- |
| **Session ID** | A unique, temporary alphanumeric token generated by the server. | Identifies the specific user and device during that visit. Persists until the browser closes or the session reaches its timeout limit. |
| **Session Cookie** | A small data file/token exchanged between the server and the user's browser. | Stored client-side; sent with subsequent requests so the server knows which user context to load without asking for login credentials again. |

> [!note] Why Tokens Matter
> Using session tokens means credentials (usernames and passwords) do not need to be transmitted across the network with every click, reducing exposure to sniffing attacks.

# Threat: Session Hijacking

> [!danger] Session Hijacking (Cookie Theft)
> An attack where an adversary steals or intercepts a legitimate user's active **session ID / session cookie**, allowing them to impersonate that user without ever knowing their password.

### How It Happens
1. **Interception:** An attacker steals the session cookie via unsecured Wi-Fi sniffing, Cross-Site Scripting (XSS), or malware.
2. **Impersonation:** The attacker injects the stolen token into their own browser requests.
3. **Bypass:** The web server trusts the valid session token and grants the attacker full access to the victim's account.

### The Single Sign-On (SSO) Multiplier Risk
If an attacker hijacks a session cookie linked to a **Single Sign-On (SSO)** service, the compromise cascades—the hijacker gains unauthorized access to **all interconnected corporate systems** tied to that user's identity.

### Defending via Accounting
Monitoring access logs helps analysts detect hijacked sessions by catching indicators of compromise (IoCs), such as:
- Simultaneous logins for the same user from two completely different IP addresses or geographic locations.
- Sudden, abnormal spikes in privilege requests during an active session.

# The Complete AAA Framework at a Glance

| Pillar | Core Question | Primary Function | Key Mechanisms / Artifacts |
| :--- | :--- | :--- | :--- |
| **Authentication** | *"Who are you?"* | Proves identity | Passwords, OTPs, Biometrics, MFA, SSO |
| **Authorization** | *"What can you do?"* | Grants specific permissions | Least privilege, Separation of duties, OAuth, API tokens |
| **Accounting** | *"What did you do?"* | Records and audits actions | Access logs, Session IDs, Cookies, SIEM tools |

---

# Exam Tips

> [!tip] Key Distinctions
> - **Accounting** = Auditing and reviewing access logs (*Who, When, What*).
> - **Access Logs:** The primary source of truth and usually the **first place** an analyst checks during an incident.
> - **Session ID:** Unique identifier attached to a user's session until logout or timeout.
> - **Session Cookie:** Token exchanged between client and server to keep user logged in without re-sending passwords.
> - **Session Hijacking:** Attacker steals an active session ID to impersonate a legitimate user.
> - **SSO Risk:** Hijacking an SSO session gives access to *multiple* internal systems at once.
